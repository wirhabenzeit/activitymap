# Activity title suggestions: prototype notes

Companion to [Places and activity visits](activity-place-inference.md). These
notes preserve the title experiment and its draft API while the main proposal
starts from a shared place catalogue and private activity relations.

Status: experimental adapters and a proposed contract, not implemented server
behaviour. The title consumer is optional and comes after place matching. It must
not define geographical visitation or block filters and statistics. The main
proposal supersedes the earlier per-activity OSM acquisition and automatic
geo-to-title scheduling plan. Applying a title remains an explicit activity edit;
inference itself performs no Strava writes.

The agreed v1 catalogue contains only peaks, passes and mountain huts represented
by points. Settlements and their start/end lookup are excluded. The existing
prototype still includes settlement candidates and fallback prompts; those are
historical experiment details below, not v1 requirements. A v1 title consumer
must use the normalized mountain-place points and abstain when their evidence
does not support a useful title, without adding settlement geocoding.

## Preliminary prompt and Gateway code

[`preliminary/jev.ts`](../scripts/prototypes/activity-names/preliminary/jev.ts)
prepares scoped geographical evidence separately from the small model context.
It reuses the historical destination-preserving filter, including cycling summit
and interior hiking settlement reserves. The latter are excluded from v1.
The legacy geometry matcher's accepted/title fields are intentionally unused.

The exact draft prompt is generated by `sportInput` in
[`jev-tuning-context.ts`](../scripts/prototypes/activity-names/jev-tuning-context.ts).
Cycling uses `minimalInput`; hiking/skiing use `decisionInput` in
[`filtered-context.ts`](../scripts/prototypes/activity-names/filtered-context.ts).
The frozen experimental modules remain unchanged. Shared state uses compact TSV
tables for route summary, features, separate encounters and high points. Each
feature has independent visit and title-role questions; historical endpoint
questions support cycling fallback and need removal for v1. Map names are
untrusted data, never instructions.

Model requests contain no activity IDs, dates, existing activity titles or raw
coordinates. They do contain route-derived distances/elevations. OSM identities
and coordinates remain in the separate geographical evidence output. Local and
English-preferred naming are explicit options.

[`preliminary/gateway.ts`](../scripts/prototypes/activity-names/preliminary/gateway.ts)
posts `{ model: "typesafe-ai/jev", state, questions }` to Gateway `/v1/evaluate`.
It accepts an API key explicitly, validates response shape and every answer
key/choice, and uses the existing local assembler. The server consumer reads
`AI_GATEWAY_API_KEY` or the established `VERCEL_AI_GATEWAY_KEY`. Credentials never
enter source, request audit JSON or error messages. The HTTP surface needs no new
AI SDK dependency and makes no import-time requests.

The experimental assembler selects supported main destinations, orders them by
encounter and removes repeated display names. More than four main destinations
requires review rather than truncation. Its settlement-based cycling loop and
start–end fallbacks are excluded from v1. The v1 consumer offers destination
titles from peaks, passes and huts, or stores an abstention. Several equally
significant mountains can belong in one title. Personal activity names are not
required answers.

Probabilities describe individual choices, not complete-title correctness or
personal preference. Do not multiply them into a title probability. Initial
results have zero or one suggestion; useful alternatives can be added later.

## Proposed API

Use the existing authenticated `/api/v1` boundary, response envelope, private/no-store
headers, canonical string IDs and structured errors. Register eventual contracts
in OpenAPI and regenerate Swift DTOs when implementing the routes.

`POST /api/v1/activity-name-suggestions` ensures work exists for 1–5 unique IDs:

```json
{ "activityIds": ["123456789"], "nameLanguage": "en" }
```

Language is `en` or `local`, default `en`. Return cached results immediately and
queue missing/stale work. Respond `202` while work is pending, otherwise `200`.
Each activity has an independent result; one unavailable activity must not discard
the others. Rate-limit newly queued work as well as HTTP traffic, so a batch cannot
bypass per-user limits.

`GET /api/v1/activity-name-suggestions?activityIds=123456789&nameLanguage=en`
only reads results and processing status. Data inside the standard envelope:

```ts
type Suggestion = {
  title: string;
  format: 'destinations';
  places: {
    id: string;
    name: string;
    kind: 'peak' | 'pass' | 'hut';
  }[];
};
type Result = {
  activityId: string;
  processing: 'idle' | 'queued' | 'running' | 'blocked' | 'failed';
  result: null | {
    outcome: 'suggested' | 'abstained';
    freshness: 'current' | 'stale';
    suggestions: Suggestion[];
    generatedAt: string;
  };
  reason?:
    | 'no_route'
    | 'unsupported_sport'
    | 'activity_unavailable'
    | 'no_candidates'
    | 'insufficient_evidence'
    | 'provider_unavailable';
  retryAfterSeconds?: number;
};
type Data = { results: Result[] };
```

The edit screen reads any cached result. The wand ensures missing work and polls
while pending. Automatic generation after ingestion is an optional later policy,
not a prerequisite for geographical matching. Applying a chosen suggestion uses
the existing activity-update endpoint.

Cache suggestions and completed abstentions by activity, language, published geo
generation, relevant place display/name revisions, and title policy/model version.
Recheck those dependencies and lease ownership before saving. A transient model
failure must not replace a usable result. The three display kinds in this early
API sketch are not the catalogue taxonomy: implementation must preserve the
source's saddle/pass and other subtypes without treating a title role as a visit.

## Evidence and remaining implementation

The two experimental sets contain 41 distinct activity IDs. On the fresh 24, the
destination-preserving filter increased title candidates from 89 to 93 and
recovered Stöcklichrüz and Oeschinensee. The latter is an existing mapped hamlet,
not a queried lake polygon, and falls outside the agreed v1 scope. Alp Wildegg is
a personal override, and Höch Hund's summit was not reached; neither personal
title is a compulsory target.

The narrow visitation rewrite cleaned Misthufen but lost a plausible Klein Mythen
suggestion. Broader wording recovered Schäfler while over-selecting elsewhere.
Reversing options changed 5/24 focused titles; repeating 17 identical requests
changed two titles. These examples are development data, not held-out accuracy
evidence. Preserve these prompts as experimental baselines; adapt and re-evaluate
them against the smaller point-based v1 catalogue before production use.

The earlier nearby category subset measured 627 OSM objects and 798 encounters
within 250 m, about 0.3 MB of compact JSON. It also allowed suburb/neighbourhood
labels; the preliminary adapter later narrowed settlements to four types, while
the agreed v1 excludes settlements entirely. These historical numbers are neither
a v1 catalogue measurement nor a proposed universal cutoff. Broader discovery
distances and repeated approaches increase persisted evidence.

The restricted query changes context relative to the historical lookup and needs
a fresh end-to-end evaluation before integration. The draft does not yet provide
exact encounter distance storage, a validated relation classifier, durable cache,
worker scheduling, authorization or transactional publication. Those belong in
the server application/repository layers rather than experimental scripts.
